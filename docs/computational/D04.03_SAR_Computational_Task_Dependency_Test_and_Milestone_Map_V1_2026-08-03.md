## 1. Purpose

This document defines the canonical computational task map for SAR pipeline rollout, including explicit task dependencies, required testing tracks, and milestone bundles.

The purpose is to support incremental issue creation without losing architectural coherence as contributors join over time.

## 2. Scope and Position

This document is delivery-facing and references the architecture and contract specifications as normative inputs.

In scope:

- generalized task graph for computational pipeline implementation,
- dependency mapping across contracts, stages, and conformance,
- testing requirements that prevent special-case drift,
- milestone bundles for staged onboarding.

Out of scope:

- personnel assignment,
- weekly sprint scheduling,
- project management tooling specifics.

### 2.1 Living Tracker Mode

This document is intended to be maintained as a living technical plan.

Tasks MAY remain in this file as the canonical dependency map while issue links and completion state are updated over time.

Tracking rules:

1. Keep task IDs stable (T01 to T27).
2. Update task status in Section 10 when work starts, moves to an issue, is blocked, or is complete.
3. Add an issue reference for each task once an issue exists.
4. Keep milestone bundle membership in Section 6 aligned with status changes.

## 6. Milestone Bundles

This section groups tasks into milestone bundles that can be opened and executed incrementally.

### 6.1 M1 Contract Core Stabilization

This milestone stabilizes the shared contract baseline before broad modality onboarding.

Included tasks:

- T01, T02, T03, T04, T05, T06

Exit criteria:

- shared envelope and identity contracts are machine-valid,
- conformance harness validates base rules,
- ingest adapter behavior for incomplete sources is auditable.

### 6.2 M2 Modality Contract Expansion

This milestone generalizes modality support while preserving one shared interface surface.

Included tasks:

- T07, T08, T09, T10, T11, T12

Exit criteria:

- profile documents for target modalities are approved,
- compatibility matrix is published,
- each profile can be validated via shared plus profile checks.

### 6.3 M3 Coherence Layer Implementation

This milestone implements deterministic L3 behavior for generalized integration.

Included tasks:

- T13, T14, T15, T16

Exit criteria:

- normalized observations are canonical,
- L3 emits deterministic state/event behavior under temporal and conflict scenarios,
- uncertainty and indeterminate outcomes are explicit and testable.

### 6.4 M4 Observability and Audit Integrity

This milestone ensures traceable runtime behavior suitable for replay and diagnostics.

Included tasks:

- T17, T23, T24

Exit criteria:

- O1 records support run/session grouping and lineage reconstruction,
- replay and degraded-state paths are validated.

### 6.5 M5 Generalization Validation Gate

This milestone proves that generalized contracts hold across modalities without special-case exceptions.

Included tasks:

- T18, T19, T20, T21, T22, T25, T26, T27

Exit criteria:

- automated tests cover contract, profile, and integration behavior,
- cross-modal tests pass without branch-per-modality exceptions at interface boundaries,
- CI quality gates enforce acceptance criteria for future sensor onboarding.

## 7. Issue Creation Packet (Per Task)

This section defines the minimum structure for opening any task issue from this map.

Required fields:

1. Task ID and title.
2. Dependency list and dependency status.
3. Normative document references.
4. Implementation scope and non-goals.
5. Required tests and pass criteria.
6. Required artifacts (code, schema, docs, logs, fixtures).
7. Definition of done.

## 8. Testing Policy Summary

This section provides the high-level quality policy that applies to all milestones.

1. No task affecting contracts is complete without automated conformance tests.
2. No modality profile is accepted without both shared and profile-specific regression coverage.
3. No L3 behavior is accepted without deterministic scenario tests for contradiction and uncertainty outcomes.
4. No pipeline release is accepted without replay and auditability validation for run and session identity continuity.
5. No new sensor onboarding is accepted without passing the standardized acceptance template.

## 9. Change Management

This section defines how this map should evolve during implementation.

1. Additive task changes SHOULD preserve existing Task IDs.
2. Breaking changes MUST include explicit migration notes and dependency updates.
3. Milestone membership MAY change as tasks split or merge, but exit criteria MUST remain explicit.
